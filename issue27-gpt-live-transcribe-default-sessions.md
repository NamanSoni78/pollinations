# gpt-live-transcribe sessions without a client session.update transcribe nothing and bill nothing — the deployment ships with transcription disabled

## Summary

`openai/gpt-live-transcribe` is billed exclusively from the usage that rides on `conversation.item.input_audio_transcription.*` events (`extractInputTranscriptionUsage`, `routes/realtime.ts`). But the deployment's **default** transcription session ships with **transcription disabled** — its `session.created` reports `audio.input.transcription: null`.

A client that simply connects and streams audio (the flow OpenAI's Realtime transcription API documents: connect → append → receive transcripts) gets:

- **no transcripts at all** — the VAD commits the speech segments (`input_audio_buffer.committed`, `conversation.item.added`), but every item shows `"transcript": null` and no `conversation.item.input_audio_transcription.*` event ever arrives;
- **a $0 bill** — with no usage-bearing events, `settleRealtimeSession` takes the no-positive-usage path, releases the API-key reservation, and charges nothing, while the provider streamed and VAD-processed the audio the whole time.

The session only transcribes — and only bills — if the client happens to send a `session.update` naming `audio.input.transcription.model`. Nothing in the route's docs or its OpenAPI description tells callers to do that, and OpenAI's own transcription sessions have transcription **on by default**. The worker test for this route (`realtime.test.ts` "serves GPT Live Transcribe through Azure and bills streamed duration") only ever exercises the session.update path against a mock that emits usage — the default-session flow was never covered, and the registry itself admits the meter was never verified live ("Azure's exact meter was not yet visible when this route launched", `shared/registry/realtime.ts`).

## Evidence

Live against `gen.pollinations.ai/realtime` with a paid key; speech generated by the platform's own `openai/tts-1` (24 kHz 16-bit mono WAV), streamed as PCM in 0.9 s chunks:

**Default session (no session.update) — 8.7 s of real speech:**

```
1x  session.created            (audio.input.transcription: null — disabled)
3x  input_audio_buffer.speech_started / speech_stopped
3x  input_audio_buffer.committed        (VAD auto-commits the speech)
3x  conversation.item.added / done      (content: [{type:"input_audio", transcript:null}])

conversation.item.input_audio_transcription.* events: 0
events carrying usage: NONE
→ session closes, settleRealtimeSession sees no positive usage → $0 billed
```

**Same session after the client sends `session.update` with `audio.input.transcription.model` — 5.65 s of speech:**

```
1x   session.created
17x  conversation.item.input_audio_transcription.delta
3x   conversation.item.input_audio_transcription.completed
     transcripts: ["Hello there.", "This is a test of the transcription system.", "Thank you for listening."]
     each completed event carries usage: {type:"duration", seconds: 1}
→ billing works: promptAudioSeconds at $0.017/min
```

(For comparison, `microsoft/mai-transcribe-2-streaming` — the other transcription route — emits `conversation.item.input_audio_transcription.completed` with `usage:{type:"duration",seconds:1}` on a plain manual-commit flow, so its sessions transcribe and bill by default. The gap is specific to the `openai/gpt-live-transcribe` deployment.)

Probe scripts: `scripts/bug-verify-wave8-livetrace-usage4.mjs` (default-session event dump), `scripts/bug-verify-wave8-livetrace-usage5.mjs` (session.update control experiment), `scripts/bug-verify-wave8-realtime-ws.mjs` (session flow).

## Root cause

- `gen.pollinations.ai/src/routes/realtime.ts` — `proxyRealtimeWebSockets` forwards client events verbatim into a session whose transcription is disabled at the provider. Nothing enables transcription by default, and nothing rejects audio streamed into an unconfigured session (the MAI path does: "Send session.update before MAI audio.").
- Billing (`extractInputTranscriptionUsage`) reads only provider usage events, which only exist once transcription is enabled — so the default session bills zero no matter how much audio streams through it.
- `gen.pollinations.ai/test/realtime.test.ts` — the only billing test for this model mocks a provider that emits usage-bearing transcription events *after a client session.update*, so the default flow's zero-transcript/zero-bill behavior was never asserted anywhere.

## Fix

Branch `solution27-realtime-default-transcription` (@ `435c9fd7`):

- `proxyRealtimeWebSockets` sends a baseline `session.update` to the provider on connect for the gpt-live-transcribe route (`allowTranscription && !mai`): `transcription.model` = the deployment, with the session's own defaults restated (pcm 24 kHz) so replacement semantics cannot drop them. A client `session.update` still overrides the baseline, and the provider's `session.updated` echo reaches the client with the public model name through the existing rewrite.
- New worker-level regression test (`test/realtime-default-transcription.test.ts`): a default session's first event at the provider is the injected `session.update` with the deployment transcription model, and the provider's echo reaches the client with the public model — RED on stock `main` (`expected 'input_audio_buffer.append' to be 'session.update'`), green after the fix.
- The existing "bills streamed duration" test now asserts the injected baseline update arrives before the client's own.

Full suite green (2874 passed), `tsc` clean, biome clean.
